1. EXECUTIVE ARCHITECTURE SUMMARY
--------------------------------------------------------------------------------
The ProjectPilot AI backend is built with a Layered MVC (Model-Schema-Service-Controller-Routes) 
pattern on Node.js (Express) using Supabase PostgreSQL.

Technology Stack Overview:
  * API Framework:      Express.js (Node.js 18+ / 20+)
  * Architectural Pattern: Layered MVC + Service Layer + Data Access Models
  * Database:           PostgreSQL hosted on Supabase
  * Data Access Layer:  @supabase/supabase-js with Service Role / RLS integration
  * Validation & Schemas: Strict Schema validation & Serialization layer (Zod / Schemas)
  * Authentication:     Supabase Auth JWT
  * Authorization:      Express Auth Middleware + Team RBAC (Member vs Lead)
  * Background Queues:  BullMQ / Redis (or Async Workers for ingestion & ML tasks)
  * AI & LLM Engine:    Groq SDK (groq-sdk), LangChain.js
  * Audio Transcription: OpenAI / Groq Whisper API for meeting audio
  * ML & Risk Scoring:  XGBoost / ONNX Runtime + SHAP Explainability Engine
  * Vector Store (RAG): pgvector in Supabase (or Chroma / LangChain VectorStore)
  * Integrations:       GitHub REST API / Webhooks & Jira Cloud REST API
  * Test Suite:         Node.js Test Runner (node:test) & node:assert / Supertest
  * Deployment:         Vercel / Docker Container / Node.js Server

Data Flow Architecture:
  Next.js Frontend (Hooks / React Query)
        ↓  (HTTP REST Request with Bearer JWT)
  Express Routing Layer (routes/)
        ↓
  Authentication & RBAC Middleware (middleware/auth.js)
        ↓
  Thin Controller Layer (controllers/)
        ↓
  Service Layer (services/ — Business Logic, Aggregations, Cross-team rules)
        ↓
  Model / Data Access Layer (models/ — Supabase PostgreSQL Queries)
        ↓
  PostgreSQL Database (Supabase with RLS & Triggers)

3. DATABASE SCHEMA & KEY ARCHITECTURAL DECISIONS
================================================================================

3.1 Core Database Tables (PostgreSQL / Supabase)

1. PROFILES (users)
   id (UUID, PK references auth.users.id)
   full_name (TEXT)
   email (TEXT)
   role (TEXT: 'developer', 'lead', 'manager')
   github_username (TEXT)
   jira_account_id (TEXT)
   created_at (TIMESTAMPTZ)

2. TEAMS
   id (UUID, PK)
   name (TEXT)
   github_repo_url (TEXT)
   jira_project_key (TEXT)
   created_by (UUID references profiles.id)
   created_at (TIMESTAMPTZ)
   updated_at (TIMESTAMPTZ)

3. TEAM_MEMBERS
   id (UUID, PK)
   team_id (UUID references teams.id ON DELETE CASCADE)
   user_id (UUID references profiles.id ON DELETE CASCADE)
   role_in_team (TEXT: 'member', 'lead')
   joined_at (TIMESTAMPTZ)
   UNIQUE(team_id, user_id)

4. SPRINTS
   id (UUID, PK)
   team_id (UUID references teams.id ON DELETE CASCADE)
   name (TEXT NOT NULL)
   start_date (DATE)
   end_date (DATE)
   planned_velocity (NUMERIC)
   actual_velocity (NUMERIC)
   status (TEXT: 'planned', 'active', 'completed')
   created_at (TIMESTAMPTZ)

5. TICKETS
   id (UUID, PK)
   team_id (UUID references teams.id ON DELETE CASCADE)
   sprint_id (UUID references sprints.id ON DELETE SET NULL)
   jira_ticket_key (TEXT)
   title (TEXT NOT NULL)
   description (TEXT)
   status (TEXT: 'todo', 'in_progress', 'in_review', 'done')
   story_points (NUMERIC)
   priority (TEXT: 'low', 'medium', 'high', 'critical')
   assignee_id (UUID references profiles.id ON DELETE SET NULL)
   ai_generated (BOOLEAN DEFAULT false)
   created_at (TIMESTAMPTZ)
   updated_at (TIMESTAMPTZ)

6. COMMITS
   id (UUID, PK)
   ticket_id (UUID references tickets.id ON DELETE SET NULL)
   team_id (UUID references teams.id ON DELETE CASCADE)
   author_id (UUID references profiles.id ON DELETE SET NULL)
   sha (TEXT UNIQUE NOT NULL)
   message (TEXT)
   files_changed (JSONB)
   lines_added (INT DEFAULT 0)
   lines_removed (INT DEFAULT 0)
   committed_at (TIMESTAMPTZ)
   created_at (TIMESTAMPTZ)

7. PULL_REQUESTS
   id (UUID, PK)
   ticket_id (UUID references tickets.id ON DELETE SET NULL)
   team_id (UUID references teams.id ON DELETE CASCADE)
   author_id (UUID references profiles.id ON DELETE SET NULL)
   pr_number (INT NOT NULL)
   title (TEXT)
   lines_added (INT DEFAULT 0)
   lines_removed (INT DEFAULT 0)
   files_changed (INT DEFAULT 0)
   test_coverage_delta (NUMERIC)
   review_count (INT DEFAULT 0)
   status (TEXT: 'open', 'merged', 'closed')
   opened_at (TIMESTAMPTZ)
   merged_at (TIMESTAMPTZ)
   created_at (TIMESTAMPTZ)

8. RISK_SCORES (Universal Shared Risk Table)
   id (UUID, PK)
   team_id (UUID references teams.id ON DELETE CASCADE)
   entity_type (TEXT: 'ticket', 'pull_request', 'user')
   entity_id (UUID NOT NULL)
   risk_type (TEXT: 'delay', 'code_aware', 'burnout')
   score (NUMERIC CHECK (score >= 0 AND score <= 100))
   shap_explanation (JSONB: { "reasons": [ { "feature": "...", "weight": 0.28 } ] })
   model_version (TEXT)
   computed_at (TIMESTAMPTZ DEFAULT now())

   * Design Rationale:
     Instead of creating fragmented tables (delay_risks, code_risks, burnout_risks), 
     one polymorphic table powers:
       - Delay Predictor (entity_type='ticket', risk_type='delay')
       - Code-Aware Risk (entity_type='pull_request', risk_type='code_aware')
       - Lead-Only Burnout (entity_type='user', risk_type='burnout')

9. MEETINGS
   id (UUID, PK)
   team_id (UUID references teams.id ON DELETE CASCADE)
   title (TEXT)
   audio_url (TEXT)
   transcript_text (TEXT)
   meeting_date (TIMESTAMPTZ)
   uploaded_by (UUID references profiles.id)
   created_at (TIMESTAMPTZ)

10. ACTION_ITEMS (Closed-Loop Meeting Verification)
    id (UUID, PK)
    meeting_id (UUID references meetings.id ON DELETE CASCADE)
    ticket_id (UUID references tickets.id ON DELETE SET NULL)
    owner_id (UUID references profiles.id)
    description (TEXT NOT NULL)
    due_date (DATE)
    status (TEXT: 'pending', 'verified_done', 'flagged_incomplete')
    verification_reason (TEXT)
    verified_at (TIMESTAMPTZ)
    created_at (TIMESTAMPTZ)

11. WORKLOAD_SNAPSHOTS
    id (UUID, PK)
    user_id (UUID references profiles.id ON DELETE CASCADE)
    team_id (UUID references teams.id ON DELETE CASCADE)
    week_start (DATE NOT NULL)
    commits_count (INT DEFAULT 0)
    prs_count (INT DEFAULT 0)
    ticket_load (INT DEFAULT 0)
    after_hours_ratio (NUMERIC DEFAULT 0)
    weekend_ratio (NUMERIC DEFAULT 0)
    created_at (TIMESTAMPTZ)
    UNIQUE(user_id, week_start)

12. SIMULATION_RUNS (Monte Carlo Sprint Simulation)
    id (UUID, PK)
    sprint_id (UUID references sprints.id ON DELETE CASCADE)
    team_id (UUID references teams.id ON DELETE CASCADE)
    scenario_description (TEXT NOT NULL)
    input_params (JSONB)
    output_results (JSONB: { "p50": "...", "p90": "...", "risk_distribution": [...] })
    run_by (UUID references profiles.id)
    created_at (TIMESTAMPTZ)

13. REPORTS (Weekly Stakeholder & Engineering Reports)
    id (UUID, PK)
    team_id (UUID references teams.id ON DELETE CASCADE)
    week_start (DATE NOT NULL)
    technical_version_text (TEXT)
    stakeholder_version_text (TEXT)
    created_at (TIMESTAMPTZ)
    updated_at (TIMESTAMPTZ)

14. NOTIFICATIONS
    id (UUID, PK)
    user_id (UUID references profiles.id ON DELETE CASCADE)
    team_id (UUID references teams.id ON DELETE CASCADE)
    type (TEXT NOT NULL)
    message (TEXT NOT NULL)
    related_entity_type (TEXT)
    related_entity_id (UUID)
    priority_score (NUMERIC DEFAULT 0)
    is_read (BOOLEAN DEFAULT false)
    created_at (TIMESTAMPTZ)

15. CHAT_MESSAGES & DOCUMENT_EMBEDDINGS (RAG Chatbot)
    chat_messages: id, team_id, user_id, role ('user'|'assistant'), content, referenced_entities, created_at
    document_embeddings: id, team_id, source_type ('ticket'|'meeting'|'report'), source_id, content_chunk, embedding (vector(384)), created_at

16. INTEGRATIONS (Encrypted OAuth Tokens)
    id (UUID, PK)
    team_id (UUID references teams.id ON DELETE CASCADE)
    provider (TEXT: 'github', 'jira')
    access_token_encrypted (TEXT NOT NULL)
    refresh_token_encrypted (TEXT)
    expires_at (TIMESTAMPTZ)
    external_account_id (TEXT)
    status (TEXT: 'connected', 'expired', 'disconnected')
    created_at (TIMESTAMPTZ)
    updated_at (TIMESTAMPTZ)

6. AUTHENTICATION & AUTHORIZATION PIPELINE
================================================================================

1. JWT Extraction:
   * Client sends: `Authorization: Bearer <supabase_jwt_token>`
   * `authMiddleware.js` verifies the token with Supabase:
     ```js
     const { data: { user }, error } = await supabase.auth.getUser(token);
     if (error || !user) return res.status(401).json({ success: false, message: 'Unauthorized' });
     req.user = user;
     ```

2. Team Context & Multi-Tenancy Resolution:
   * Service layer resolves user team membership:
     ```js
     const { data: member } = await supabase
       .from('team_members')
       .select('team_id, role_in_team')
       .eq('user_id', req.user.id)
       .maybeSingle();
     ```
   * Any resource accessed must match `req.team_id`. Cross-team queries strictly return 404.

3. Role-Based Access Control (Lead vs Member):
   * Burnout scores and sensitive workload features are guarded by `requireLead` middleware:
     ```js
     if (member.role_in_team !== 'lead') {
       return res.status(403).json({ success: false, message: 'Forbidden: Team Lead access required' });
     }
     ```
